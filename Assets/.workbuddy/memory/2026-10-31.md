## WebGL 加载优化——第一批导入设置（09:30）
- 背景：WebGL 加载慢。10-30 构建：data.unityweb 46.5MB（gzip），wasm 6.9MB。构建报告（Editor-prev.log 4941 行起）：Meshes 39.4MB (50.7%) + Textures 36.4MB (46.3%)。
- 瘦身点定位：Textures = 39 张手指图层 PNG（1920×1080，DXT5 后每张 ~920KB）；Meshes = 两个 FBX（Keyboard68_Gloss.fbx 源 110MB 高模，已 meshCompression:3 无油水；Keyboard68.fbx 源 42MB，原 meshCompression:0）。
- 已改（直接编辑 .meta，回 Unity 触发 reimport）：
  1. 39 张 hl_*.png 的 DefaultTexturePlatform maxTextureSize 2048→1024（预计 Textures 36→~9MB）
  2. Keyboard68.fbx meshCompression 0→1（Candy 场景模型，量化有轻微风险）
- 不能做的：两个 FBX 均需 isReadable:1（RewriteCapUv 运行时改 UV），不能关；Gloss 已是最高压缩。
- 待用户 Build 后对比 data.unityweb 体积（预期 46.5→~28-30MB）。
- 后备手段（若还要压）：① Build Settings 移除 Candy 场景（省整个 Keyboard68.fbx 的网格）；② 手指贴图再降到 768/512；③ wasm 6.9MB 可关异常支持（牺牲报错信息）。
- 提醒过用户：Mesh 压缩有损（顶点/UV 量化），若 Candy 场景出现几何/UV 抖动，回滚 Keyboard68.fbx.meta 的 meshCompression。

## 加载优化第二轮——剥离切线（09:58）
- 用户已 Build（09:53）：data.unityweb 45.0MB，只减 1.5MB？错——看新构建报告（Editor.log 3223 行）：Textures 36.4→10.9MB ✓（hl_* 每张 268KB，第一轮生效），但 Meshes 仍 39.4MB，且其中 **Keyboard68_Gloss.fbx 单独占 39.4MB (58%)**——主场景模型就是全部体积瓶颈，且已 meshCompression:3 无油水。Keyboard68.fbx 未出现在报告（网格与 Gloss 去重或 Candy 复用 Gloss 模型）。
- 新构建 gzip 比率差的原因：网格数据几乎不可压。
- 第二轮：两个 FBX 的 tangentImportMode 3(Import)→0(None)。依据：FBX 无任何贴图（构建 Textures 仅手指图层）→ 材质无法线贴图 → 切线可剥；全工程 grep tangent 无引用。预期每顶点省 16B（约省 1/3 网格），data 预期 45→~33MB。
- 长期根治（用户侧）：Gloss.fbx 源文件 110MB，网格密度病态（一个键盘 39.4MB 顶点数据），建模软件里减面/降细分重导出才是真正解法。
